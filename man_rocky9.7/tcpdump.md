# tcpdump(8) — dump traffic on a network

`tcpdump` はネットワークインタフェース上のパケットをキャプチャして表示/保存するツールです。

- 「SYN が出ている/返ってきている？」
- 「DNS 問い合わせは飛んでいる？」
- 「再送してない？（遅いのはネットワーク？アプリ？）」

といった、**“実際に線を流れているもの”**で切り分けたいときに強いです。

注意：パケットキャプチャは情報を含み得ます。必ず**管理下のホスト/ネットワーク**で、必要最小限（フィルタを付ける）で使います。

## まず結論：よく使うコマンド

```bash
# 0) まずIF一覧（どのインタフェースで捕まえるか決める）
tcpdump -D

# 1) 最初の定番（名前解決しない、IF指定、数十パケットだけ）
# -n: 逆引きしない（速い・DNS影響排除）
# -i: インタフェース
# -c: 件数で止める
sudo tcpdump -n -i eth0 -c 50

# 2) 特定の宛先/ポートだけ（最重要：最初から絞る）
sudo tcpdump -n -i eth0 -c 200 host 203.0.113.10 and port 443

# 3) DNS だけを見る（UDP/TCP 53）
sudo tcpdump -n -i eth0 -c 200 port 53

# 4) pcap に保存して後で見る（調査の証跡にする）
# -w: 書き込み（表示しないで保存）
sudo tcpdump -n -i eth0 -w /tmp/capture.pcap host 203.0.113.10

# 5) 保存した pcap を読む（権限は不要なことが多い）
# -r: 読み取り
# -nn: ポート名解決もしない（80→http等にしない）
tcpdump -nn -r /tmp/capture.pcap

# 6) パケットの中身も見たい（ヘッダ+ヘクス+ASCII）
# -X: hex + ASCII
sudo tcpdump -n -i eth0 -c 20 -X host 203.0.113.10 and port 80

# 7) “疎通が怪しい”の最短（SYN/SYN-ACK/ACK が見えるか）
sudo tcpdump -n -i eth0 -c 200 tcp and host 203.0.113.10 and port 443
```

## SYNOPSIS（書式）

```text
tcpdump [options] [expression]
```

- `options`：表示方法/保存方法/インタフェース等
- `expression`：どのパケットを取るか（BPF フィルタ）

`expression` を付けないと“全部”取ろうとして重く/危険なので、基本は最初から絞ります。

## 最重要オプション（運用で効くもの）

### どこで捕まえるか

- `-D`：インタフェース一覧を表示
- `-i interface`：キャプチャするインタフェースを指定

### 名前解決の無効化（最初に付ける）

- `-n`：アドレスの名前解決をしない（逆引きしない）
- `-nn`：さらにポート番号も名前解決しない（`80` を `http` にしない）

名前解決が入ると、

- 表示が遅くなる
- DNS 自体の障害/遅延が “tcpdump の表示”に混ざる

ので、調査の初動は `-n`（できれば `-nn`）が無難です。

### いつ止めるか（無限に取らない）

- `-c count`：指定パケット数で終了

本番運用では、まず `-c` で短く状況を掴みます。

### どこまで取るか（snaplen）

- `-s snaplen`：1パケットから保存/表示する最大バイト数

- デフォルトの `snaplen` は環境によっては小さく、アプリ層が途中で切れることがあります
- “全部欲しい”なら `-s 0`（環境によって意味は異なり得ますが、概ね最大まで取る意図）

ただし、取り過ぎるとファイルも大きくなるので、まずはフィルタで絞るのが先です。

### 保存と読み取り（調査の証跡）

- `-w file`：pcap として保存（画面表示はしない）
- `-r file`：pcap を読み取り

運用では、

1) `-w` で証跡を残す
2) あとで `-r` で読み返す/共有する

が強いです（Wireshark に渡すこともできます）。

### 表示（見やすさ）

- `-v`/`-vv`/`-vvv`：詳細度を上げる
- `-q`：簡潔表示
- `-A`：ASCII で表示（テキストっぽいとき）
- `-x`：ヘクスダンプ
- `-X`：ヘクス + ASCII

## expression（BPF フィルタ）の使い方

`expression` は「欲しいパケットだけ」を指定するフィルタです。

- 基本演算子：`and` / `or` / `not`
- まずは `host` と `port` で絞るのが最も効きます

### よく使うフィルタ例

```bash
# 特定ホストだけ
host 203.0.113.10

# 宛先（サーバ）っぽい側に寄せる
dst host 203.0.113.10

# 特定ポートだけ
port 443

# サブネット
net 192.168.0.0/16

# プロトコル
icmp
arp
udp
tcp

# “DNS だけ”
port 53

# “HTTP/HTTPS っぽい”
port 80 or port 443

# 外向きだけ見たい（例: ローカル→外部の 443）
src host 192.0.2.10 and dst port 443
```

### フィルタはクォートすると安全

シェルが `(` `)` `!` などを解釈して事故りやすいので、複雑になったらクォートします。

```bash
sudo tcpdump -n -i eth0 '(host 203.0.113.10 and (port 80 or port 443))'
```

## 読み方の最短メモ（疎通/遅延の初動）

### TCP の疎通

- クライアント→サーバへ `SYN`
- サーバ→クライアントへ `SYN, ACK`
- クライアント→サーバへ `ACK`

が見えていれば、TCP のハンドシェイクは成立しています。

- `SYN` だけ見えて `SYN,ACK` が返らない：
  - サーバに届いていない（経路/FW）
  - サーバが落としている（FW/Listenしてない）
  - 非対称経路（戻りが別経路）

…などを疑います。

### DNS の切り分け

`port 53` で、問い合わせ（query）と応答（response）が出ているかを見ます。

- query が出てない：アプリ/ホスト側の問題（resolver設定、ライブラリ、FWなど）
- query は出るが応答が無い：DNSサーバ到達性/FW/上流障害など

## 権限（capability）

ライブキャプチャ（インタフェースから読む）は権限が必要になることがあります。

- うまくいかないときはまず `sudo tcpdump ...`
- pcap ファイルの読み取り（`-r`）は権限不要なことが多いです

## 終了コード（exit status）

`man tcpdump` には独立した「EXIT STATUS」節が見当たりませんでした。

この環境での簡単な実測：

- `tcpdump --help` は `0`
- `tcpdump -r /no/such/file.pcap` のように読めない入力は `1`

とはいえ、運用上は「stderr のエラーメッセージ」も含めて判断するのが安全です。

## 事故りポイント（tcpdump あるある）

- フィルタ無しで取らない（量が多い・情報を含む・ディスクを食う）
- `-n`/`-nn` を付けないと、名前解決の遅さが混ざって“症状”がブレる
- キャプチャ対象 IF を間違える（`-D` で確認 → `-i`）
- ループバックは重複して見えることがある（OS/設定に依存）
- `-s` が小さいと “肝心な部分が切れている” ことがある（必要なら `-s 0` + フィルタで絞る）

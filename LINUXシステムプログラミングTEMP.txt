UmuOSの為のLinuxシステムプログラミング

このノートは、UmuOSを進化させるためにプロセス管理・メモリ管理・ファイルI/O・シェル・システムコール設計に
直接役立つ形で抽象化し、再構成することであります。
すなわち、UmuOSの構造へ還元するための実践ノートである。
LinuxのAPIやシステムコールは、OSがどのようにふるまうかでもあり、その構造を理解することはUmuOSの設計力を
高めることに直結するとおもう。

1章
概要および主要概念
1
　本書はシステムプログラミング（system programming）、すなわちシステムソフトウェア（system software）
開発の真髄を解説するものです。システムソフトウェアはシステムの下位に位置し、カーネルや主要なシス
テムライブラリを直接操作します。よく利用されるシェル、テキストエディタ、コンパイラ、デバッガなど
の主要ツールやシステムデーモンもシステムソフトウェアです。これらのコンポーネントは、カーネルおよ
びCライブラリの上に成り立つ完全なシステムソフトウェアです。GUIアプリケーションなど他のソフト
ウェアはほとんどがより上位に位置し、下位のソフトウェア、ハードウェアへアクセスすることは極めてま
れか、もしくは全くありません。来る日も来る日も一日中システムソフトウェアを開発するプログラマもい
ますし、仕事のごく一部としてシステムソフトウェアに関わるプログラマもいます。しかし、システムプロ
グラミングに対する理解はすべてのプログラマに必須と言えます。システムプログラミングを、これこそプ
ログラマの存在理由であると考えても、またはより上位のシステム概念の単なる土台としてとらえてもどち
らでも構いませんが、すべてのソフトウェア開発の根底に存在することは変わりありません。
　本書では特にLinuxでのシステムプログラミングを中心に述べます。LinuxはUnixライクなシステムで、
Linus Torvaldsおよび世界中のハッカーコミュニティ（厳密なものではありません）によりゼロから開発され
ています。Linuxの目指すものや思想はUnixと変わりありませんが、Linux自身はUnixではありません。
Linux では独自の路線を採り、現実的な機能を重視し、独自のゴールに向かっています。Linuxシステムプ
ログラミングの本質は、他のUnixシステムと一般的には変わりませんが、古典的なUnixシステムと比較し
た場合、基礎レベルでは等価ですが、より高度なレベルでLinuxは進化しており、システムコールを追加し、
動作を改善し、新機能なども多数備えています。
1.1　システムプログラミング
　古くは、すべての
Unixプログラミングはシステムレベルのプログラミングだったと言えます。歴史的に
は、Unixシステムは上位の抽象概念をそれほど多くは備えていませんでした。Xウィンドウシステムなどの
開発環境を使用したプログラミングでも、下位のUnixシステムAPIが全般的に使用されていました。この
ため、本書は一般的Linuxプログラミングの解説書とも言えます。しかし、本書ではLinuxプログラミング
環境については触れません。makeの使用法などの説明はありません。本書が解説するのは、現代のLinuxマ
シンで使用可能なシステムプログラミングAPIについてです。
2 1章　概要および主要概念
　システムプログラミングは常にアプリケーションプログラミングと比較されます。システムレベルとアプ
リケーションレベルのプログラミングでは、異なる部分もありますが、すべてがそうではありません。シス
テムプログラミングでは、使用するハードウェアおよびオペレーティングシステムをプログラマが十分に意
識する必要があります。もちろん使用するのがライブラリかシステムコールかという違いもあります。開発
するアプリケーションに必要な下位モジュール/ライブラリにも依存しますが、ライブラリとシステムコー
ルは簡単には置換できません。しかし一般的には、アプリケーションプログラミングからシステムプログラ
ミングへの移行はそれほど困難ではありません。逆も同様です。アプリケーションが他の多くのモジュール/
ライブラリに依存しており、システムの最下層からずっと上位に位置していても、システムプログラミング
の知識は大きな意味を持ちます。このことはすべてのプログラミングに共通して言えることです。
　アプリケーションプログラミングのここ何年かの傾向として、システムレベルのプログラミングから離れ、
非常に上位レベルでの開発に向かっていることがうかがえます。JavaScriptやPHPなどのWebソフトウェ
アや、C#やJavaなどで使用される中間言語がそうです。この傾向は、システムプログラミングの終焉を予
言するものではありません。上位ソフトウェアが流行しても、JavaScriptインタプリタやC#ランタイムライ
ブラリなどの下位ソフトウェア開発は必須であり、これはまさにシステムプログラミングです。また、PHP
やJavaを使用する開発者にとっても、システムプログラミングの知識は大きな恩恵をもたらします。ソフト
ウェアの上位、下位を問わず、システムのコアに対する理解は良質のコーディングへつながります。
　アプリケーションプログラミングの流行に反するわけではありませんが、UnixやLinuxでは大部分のソー
スコードが今もシステムレベルで記述されています。そのほとんどはC言語で、使用するインタフェースの
大部分はCライブラリとカーネルにより提供されています。これがシステムプログラミングで、Apache、
bash、cp、Emacs、init、gcc、gdb、glibc、ls、mv、vim、X ウィンドウシステムもそうです。これらの
アプリケーションがすぐになくなることはありません。
　システムプログラミングの範疇には、カーネル開発または少なくともデバイスドライバ開発を含めて議論
することが多いのですが、本書では（システムプログラミングの他の多くの書籍もそうですが）、カーネル開
発には触れません。その代わりに、ユーザによるシステムレベルのプログラミングを詳細に解説します。
カーネルより上位のものすべてを含みます（もちろんカーネル内部の知識があれば本書でも大きな助けにな
るでしょう）。その他のソケットなどネットワークプログラミングも本書では触れません。デバイスドライ
バ開発やネットワークプログラミングは大規模であり、膨大な内容になるため、このテーマに絞った専門の
書籍が必要になるでしょう。
　システムレベルのインタフェースとはなんでしょう。本書はこの疑問および以下のような疑問に答えるた
めのものです。
● Linuxでシステムレベルのアプリケーションを開発するにはどうすれば良いか。
● カーネルやCライブラリが提供するものは具体的に何か。
● 効率的なソースコードを記述するには、またLinuxではどんな仕掛けが用意されているか。
● 他のUnixシステムと比べて、Linuxではどんな巧妙なシステムコールが用意されているか。また、どん
な動作をするのか。
Linux のシステムプログラミングでは重要なものが3つあります。システムコール、Cライブラリ、Cコ
ンパイラです。まずそれぞれについて概要をまとめます。
1.1　システムプログラミング
1.1.1　システムコール
　システムプログラミングの入口に相当するものがシステムコールです
（system call。syscall と短縮される
こともよくあります）。システムコールとは、テキストエディタや読者も好きなゲームなど、ユーザ空間か
らオペレーティングシステムに何らかの動作やリソースを要求するための、カーネル（システムのコア、中
核）機能を呼び出すものです。read()やwrite()などよく利用されるものから、get_thread_area()や
set_tid_address()などめったにお目にかかれないものまで、幅広く用意されています。
Linuxで実装されているシステムコールは他のオペレーティングシステムのカーネルに比べ、ずっと数が
少なくなっています。例えば、現在のi386アーキテクチャ用のシステムコール数はおよそ300になりました
が、Microsoft Windowsのシステムコールは数千にも上るそうです。LinuxカーネルではAlpha、i386、PowerPC
などマシンアーキテクチャごとにシステムコールを用意しています。このため、あるアーキテクチャでは使
用可能なシステムコールでも、他のアーキテクチャでは対応していない場合もあります。とは言っても、大
部分のシステムコール（90%以上）はすべてのアーキテクチャで実装されています。本書で解説するのは、こ
の共通部分のシステムコールです。
1.1.1.1　システムコールの発行（コール）
　ユーザ空間のアプリケーションをカーネル空間へ直接リンクすることはできません。セキュリティや信頼
性の問題があるため、ユーザアプリケーションが直接的にカーネル内のコードを実行したり、データを操作
することは禁止されています。このためカーネルは、ユーザアプリケーションのシステムコール発行（呼び
出し、コール。カーネル機能の要求）に、その実現方法も含め、対応する必要があります。カーネルが定義
した方法にしたがえば、アプリケーションからカーネルへ入り（trap）、許可された範囲でカーネルコードを
実行できます。要求方法の実際はアーキテクチャによりまちまちです。i386システムでは、ユーザアプリケー
ションがソフトウェア割り込み命令intを実行します。割り込み番号は0x80です。この割り込み命令によ
りカーネル空間、すなわちソフトウェア割り込みハンドラを実行するカーネル内の保護された空間へと切り
替わります。0x80番の割り込みを処理するハンドラこそが、システムコールを受け付ける本体です。
　アプリケーションはカーネルに対し、実行するシステムコールを通知し、CPUのレジスタ（machine
register）へそのパラメータをセットします。システムコールには0から始まる番号が割り振られています。
例えばi386アーキテクチャでシステムコール番号5（open()の番号です）を通知する場合は、アプリケーショ
ンはint命令を実行する前に、5をeaxレジスタにセットします。
　システムコールのパラメータをカーネルに渡す場合も同じ要領です。例えばi386で5つまでのパラメータ
を渡す場合は、ebx、ecx、edx、esi、ediの各レジスタに、この順序でパラメータをセットします。6つ以
上のパラメータを使用するシステムコールもまれに存在しますが、この場合は、すべてのパラメータを格納
したバッファ（ユーザ空間）へのポインタを1つセットします。言うまでもないことですが、ほとんどのシス
テムコールは2、3のパラメータしか使用しません。
　他のアーキテクチャではシステムコールの発行手順は異なりますが、本質は変わりません。システムプロ
グラマは通常、カーネルがシステムコールをどのように受け付けるかを把握しておく必要はありません。こ
の手順はアーキテクチャにより定められており、コンパイラとCライブラリにより自動的に処理されます。

4 1章　概要および主要概念
1.1.2　Cライブラリ
Cライブラリ（libc）はUnixアプリケーションの心臓部分です。C言語以外でプログラミングした場合でも、
上位ライブラリにより隠蔽されているかもしれませんが、コアサービスやシステムコールを利用するために
Cライブラリは使用されています。LinuxシステムのCライブラリはGNU libcです。glibc（ジーリブシー）
と短縮して呼ばれます（一般的ではありませんが、グリブシーと呼ぶ場合もあります）。
GNU Cライブラリは多くの機能を備えています。標準Cライブラリ関数だけではなく、glibcではシス
テムコールラッパ、スレッド対応、アプリケーションで必要になる基本機能なども備えています。
1.1.3　Cコンパイラ
Linuxでは、標準のCコンパイラはGNU Compiler Collection（gcc）です。もともとgccという名前はCコ
ンパイラccのGNUバージョンを表し、GNU C Compilerの頭文字をとったものでした。その後、非常に多
数の他の言語にも対応したため、現在ではGNUコンパイラファミリの総称となっています。しかしながら、
gccはCコンパイラを起動するコマンドの名前でもあります。本書でgccと記述した場合は、通常はgccコ
マンドを指します。必要に応じ文脈から適宜判断してください。
Linuxを含むUnixシステムで使用するコンパイラは、システムプログラミングと密接な関係があります。
C言語仕様（「1.3.2　C言語仕様」を参照）およびシステムABI（「1.2　APIとABI」を参照）に対応するのはコ
ンパイラです。この点については本章で後述します。
1.2　APIとABI
　元来プログラマは、予定したシステムのすべてでアプリケーション
†が動作するように開発しますし、ま
た将来に渡っても動作が保証されるように注意を払い、開発に使用したLinuxディストリビューション以外
のディストリビューションでも動作し、また他のアーキテクチャのLinuxや将来の（または過去の）バージョ
ンのLinuxでも動作することを期待します。
　システムレベルの観点では、移植性に影響を与えるものには2種類あります。API（アプリケーションプロ
グラミングインタフェース、application programming interface）と ABI（アプリケーションバイナリインタ
フェース、application binary interface）です。APIもABIも異なる種類のソフトウェア間のインタフェース
を定義するものです。
1.2.1　API
APIとは、ソフトウェア間のソースレベルでのインタフェースを定義したものです。他のソフトウェアか
ら呼び出し可能なインタフェース（通常は関数）の標準セットを定義し、抽象化したものです。通常は上位ソ
フトウェアから下位ソフトウェアの機能を呼び出します。例えば、テキストを画面上に描画するのに必要な
処理、機能すべてを概念的に抽象化し、複数の関数として定義したものがAPIです。APIはインタフェース
を定義するものに過ぎません。APIを提供するソフトウェアを、APIの実装（implementation）といいます。
† 訳者注：ユーザ空間で動作するソフトウェアを、ツール、ユーティリティ、アプリケーションなどに分類するこ
ともありますが、本訳では総称してアプリケーションと呼びます。
1.2　APIとABI
APIは「契約」と言われることも多いのですが、少なくとも法律的な意味では、正しくありません。双方
の合意に基づいたものではないためです。APIのユーザ（通常は上位ソフトウェア）はAPIの策定にも実装に
も一切口を挟んでいません。ユーザはAPIをそのまま使用するか、または全く使用しないかです。双方のソ
フトウェアがAPIにしたがっている場合に限り、動作は保証され、ソースレベルの互換性（source
compatible）が保たれます。すなわち、APIのユーザがその実装を正しく利用できます。
　実際の例として、C言語仕様および標準Cライブラリで実装されたAPIがあります。文字列操作など基礎
的かつ本質的な関数を定義したAPIです。
本書では、多くの既存APIを利用します。例えば「3章　I/Oのバッファリング」では、標準入出力ラ
イブラリを使用します。Linuxシステムでもっとも重要なAPIについては、本章の「1.3　標準仕様」で後述
します。
1.2.2　ABI
APIがソースレベルのインタフェースを定義するのに対し、ABIは特定のアーキテクチャにおけるソフト
ウェア間の低レベルなバイナリインタフェースを定義したものです。アプリケーションが自身やカーネル、
ライブラリと何らかの情報をやり取りする際に使用する方法です。ABIが保証するのはバイナリレベルの互
換性（binary compatibility）です。ABIが同一ならば、リコンパイルせずともオブジェクトコードはどんなシ
ステムでも動作することが保証されます。
ABIが定義するものは、呼び出し規約（calling convention）、バイトオーダ、レジスタの使用、システムコー
ルの発行、リンク、ライブラリの動作、バイナリオブジェクト形式などです。呼び出し規約では、例えば、
次のような内容を定義します。
● 関数コールの方法
● 関数パラメータの渡し方
● 値が維持される、またはされないレジスタ
● 関数の戻り値の受け取り方
1つのアーキテクチャに対しては1つのABIを策定し、複数の異なるオペレーティングシステム間で共有
する試みがこれまでに何度かなされました。特にi386のUnixシステムがそうです。しかし、満足のいく成
果は得られず、Linuxもそうですが、オペレーティングシステムは自身にとって最適と考えるABIを独自に
定義するようになりました。ABIはアーキテクチャに密接に関係するものです。ほぼすべてのABIは、レジ
スタやアセンブリ命令など、マシン固有の実装に依存します。このため、Linuxでもマシンアーキテクチャ
ごとにそれぞれのABIを定義しています。実際には、alpha、x86-64†など、あるABIを指してマシン名で呼
んでいます。
　システムプログラマはABIには常に注意を払うべきです。しかし、丸暗記する必要はありません。ABIを
決定するのはコンパイラ、リンカなどのツールチェイン（toolchain）であり、通常は他の場面では登場しませ
ん。ABIに関する知識は効率の良い上質のプログラミングに役立ちますし、アセンブリコードを記述する場
合やツールチェインをハッキング（これはすなわちシステムプログラミングです）する場合には必須となります。
† 訳者注：歴史的経緯によりamd64という呼び方も残っています。

1.3　標準仕様
Unixシステムプログラミングは古典的な技術です。Unixプログラミングの基本は数十年間変化していま
せんが、Unixシステム自体はどんどん変化しており、動作は変更され、機能も追加されています。混乱に拍
車をかけるように、複数の標準化グループがシステムインタフェースを策定し、それぞれ公的な標準を設け
ました。標準は複数存在しますが、技術的に言えばLinuxはどの標準にも正式にはしたがっていません。
Linux ではもっとも重要でかつ普及している2つの標準に準拠することを目標にしています。POSIX
（Portable Operating System Interface）とSUS（Single UNIX Specification）です。
　他の標準もそうですが、POSIXおよびSUSではUnixライクなオペレーティングシステムインタフェース
のC言語APIを明文化しています。言い換えれば、Unixシステムに準拠したシステムプログラミング、ま
たはその最低限のサブセットを定義しています。
1.3.1　POSIXとSUSの歴史
1980年代中頃に、IEEE（Institute of Electrical and Electronics Engineers）が Unixシステムのシステムレ
ベルインタフェース標準化策定の先陣を切りました。現在のFree Softwareの創始者とも呼ばれるRichard
Stallmanが、標準の名前としてPOSIX（パーズィックスと読みます†）を提案し、今ではPortable Operating
System Interface の頭文字を並べたものとされています。
　最初の成果は1988年にIEEE Std 1003.1-1988（略してPOSIX 1988と呼ばれます）として発表され、その後
1990年にIEEE Std 1003.1-1990（POSIX 1990）で改訂されました。オプションとしてリアルタイム対応、ス
レッド対応もそれぞれIEEE Std 1003.1b-1993（POSIX 1993またはPOSIX.1b）、IEEE Std 1003.1c-1995（POSIX
1995またはPOSIX.1c）で策定されました。2001年になると、オプションもPOSIX 1990へ統合され、新しい
1つの標準としてIEEE Std 1003.1-2001（POSIX 2001）が公開されました。現在の最新バージョンは2004年
4月に策定されたIEEE Std 1003.1-2004です。このバージョンのPOSIXのコア全体を指し、POSIX.1と呼び
ます。
1980 年代後半から1990年代初頭にかけ、Unixシステムのベンダ達は「Unix Wars」状態に入り、それぞ
れのUnixこそが正当に定義されたUnixオペレーティングシステムであるとの主張を戦わせました。その中
で主要なベンダ数社が再結集し、OSF（Open Software Foundation）とX/Openを合併し、業界団体The Open
Groupを結成し、認定証や技術白書の発行、準拠の確認テストなどを行うようになりました。1990年代初頭
のUnix Warsの最中に、The Open GroupがSUS（Single UNIX Specification）を公開すると、急速に普及し
ました。大きな要因はPOSIX標準が有償で高くつくのに対し、SUSは無償で入手可能だったためです。今

1.4.1.4　シンボリックリンク
　ハードリンクは異なるファイルシステムにまたがることはできません。inode番号はそのinodeが存在す
るファイルシステム外では意味を持たなくなるためです。ファイルシステム間をまたぐリンクは透過性は高
くありませんが単純なため、Unixシステムではシンボリックリンク（symbolic link）†も備えています（一般に
symlink と省略されます）。
　シンボリックリンクも通常ファイルと同様に扱えます。シンボリックリンクは自身のinodeとデータを持
ち、シンボリックリンク先のパス名を保持します。この仕組みによりシンボリックリンクではどんな場所に
あるものでも参照可能になります。異なるファイルシステムに存在するファイルやディレクトリも参照可能
ですし、存在しないものでも参照先として使用できます。存在しないファイルを参照するシンボリックリン
クをbroken link と呼びます。
　ハードリンクに比べ、シンボリックリンクはオーバヘッドが大きくなります。シンボリックリンクをたど
るにはシンボリックリンク自身のパス解決に加え、参照先ファイルのパス解決も必要になるためです。ハー
ドリンクではこのオーバヘッドは発生しません。リンクカウントが1のファイルでも、2以上のファイルで
もアクセスに差はありません。シンボリックリンクのオーバヘッドは最低限に抑えられていますが、それで
も肯定的にはとらえられていません。
　ハードリンクに比べればシンボリックリンクの透過性‡は高くありません。ハードリンクは完全に透過で、
複数リンクされていることも検知できます。シンボリックリンクの操作は専用のシステムコールを必要とし
ますが、この非透過性もハードリンクよりも高度なショートカットとして機能するため、許容する向きもあ
ります。
1.4.1.5　スペシャルファイル
スペシャルファイル（特殊ファイル、special file）はファイルとして表現されたカーネルオブジェクトです。
長年に渡り、Unixシステムはさまざまなスペシャルファイルに対応してきました。Linuxでは4種類のスペ
シャルファイルに対応しています。ブロックデバイス、キャラクタデバイス、名前付きパイプ（named pipe）、
Unixドメインソケットです。スペシャルファイルは、抽象化した概念をファイルシステム内にきれいに収め

ルファイルを作成するシステムコールを備えています。

1.4　Linuxプログラミングの概念
常ファイルのようにファイルシステム上に存在するものです。デバイスファイルはオープン、読み取り、書
き込みが可能で、ユーザ空間からシステムのデバイス（実デバイス、仮想デバイスともに）へのアクセス、操
作が可能です。Unixのデバイスは一般的に2種類に分類されます。キャラクタデバイス（character device）
とブロックデバイス（block device）です。デバイスそれぞれに専用のデバイスファイルが存在します。
　キャラクタデバイスはバイトがリニアに並んだものとしてアクセスし、デバイスドライバがキューにデー
タを1バイトずつ置き、ユーザ空間からキューに置かれたデータを読み取ります。キャラクタデバイスの典
型的な例はキーボードです。例えば、ユーザが「peg」と入力した場合、アプリケーションはキーボードデ
バイスからp、e、gというデータが、この順序の通りに読み取れることを期待します。データがなくなると
デバイスはEOF（ファイル終端、end-of-file）を返します。入力された文字を無視したり、異なる順序で読み
取ることは意味がありません。キャラクタデバイスへはキャラクタデバイスファイル（character device file）
を介してアクセスします。
　対称的にブロックデバイスは、データをバイト配列としてアクセスするものです。デバイスドライバは
シーク可能なデバイスにデータバイトをマッピングし、ユーザ空間からはバイト配列内ならばどのバイトに
もアクセス可能です。順序も関係ありません。12番目のバイトを読み取り、次に7番目のバイトを読み取っ
た後でも、再び12番目のバイトへアクセスできます。ブロックデバイスは通常ストレージデバイスです。
ハードディスク、フロッピーディスク、CD-ROM、フラッシュメモリなどはすべてブロックデバイスです。
ブロックデバイスへはブロックデバイスファイル（block device file）を介し、アクセスします。
名前付きパイプ（named pipe。「先入れ、先出し」、「first-in、first-out」を縮めてFIFOとも呼ばれます）は
IPC（プロセス間通信、interprocess communication）の仕組みの1つで、スペシャルファイルのファイルディ
スクリプタを介した通信チャネルです。アプリケーションの出力を他のアプリケーションの入力へと「つな
ぐ」機能を持つ通常のパイプは、システムコールによりメモリ上に作成されるものでファイルシステム上に
存在するものではありません。名前付きパイプは通常のパイプと同様に扱えますが、FIFOスペシャルファ
イル（FIFO special file、または単にFIFO）というファイルを介してアクセスします。親子関係など特に関係
を持たないプロセス同士でも、FIFOスペシャルファイルを介し通信可能です。
　最後に挙げるスペシャルファイルはソケット（socket）です。ソケットはIPCが進化したもので、プロセス
間の通信に使用します。同じマシン内のプロセスに限定せず、異なるマシン間でも通信可能です。実際、ソ
ケットはネットワークやインターネットを使用したプログラミングの基本です。ソケットにはいろいろな種
類があり、Unixドメインのソケットはソケットの形を取っていますが、同一マシン内での通信にしか使用で
きません。インターネットを経由したソケット通信はホスト名とポート番号の組を用いて通信先を特定しま
すが、Unixドメインソケットではファイルシステム上に存在するスペシャルファイルを用いて特定します。
Unix ドメインソケットは単にソケットファイルとも呼ばれます。

1.4.2　プロセス
Unixシステムでもっとも基本的かつ重要な概念をファイルとしたら、次に重要なものはプロセスです。プ
ロセスとは実行状態にあるオブジェクトコードのことで、実行中のプログラムがそうです。しかし単なるオ
ブジェクトコードだけではなく、プロセスにはデータ、リソース、状態、仮想コンピュータなども含みます。
　プロセスは実行可能オブジェクトコードから生成されます。カーネルが解釈可能な実行形式ファイルに収
められた、マシンが実行可能なオブジェクトコードです（Linuxでもっとも広く利用されている実行形式は
ELFです）。実行形式にはメタデータおよびセクションが収められ、セクションにはコードセクション、デー
タセクションがあり、また複数になる場合もあります。セクションとはオブジェクトコードをリニアに保存
したもので、メモリにもリニアにロードされるものです。セクション内のすべてのバイトは同様に処理され、
同じパーミションを与えられ、通常は使用目的も同じになります。
　もっとも重要で頻繁に使用されるセクションはテキストセクション（text section）、データセクション（data
section）、bssセクション（bss section）です。テキストセクションは実行コードおよびプログラムで使用す
る定数などの読み取り専用のデータを保存したもので、通常は読み取り専用と実行可能のマークが付けられ
ます。データセクションはプログラムで初期化した変数などの初期化済みデータを持ち、通常は読み取り/
書き込み両方可能のマークが付けられます。bssセクションには未初期化のグローバルデータが置かれてい
ます。C言語仕様では変数のデフォルト値は本質的にすべて0のため、ディスク上のオブジェクトコードに
0を改めて埋める必要はなく、未初期化の変数の一覧をbssセクションのオブジェクトコードに保存してお
き、セクションをメモリへロードする際にカーネルがゼロページ（zero page。内容がすべてゼロのページ）を
マッピングします。bssセクションはまさにこのことを念頭に開発されたものです。bssという名前は歴史的

連するデータや統計情報はカーネル内のプロセスディスクリプタ（プロセス記述子、process descriptor）に保
持されます。

1.4.2.1　スレッド
　プロセスには1つまたは複数のスレッド（実行スレッド、threads of execution）があります。スレッドとは
プロセス内の実行単位で、処理実行を担当する抽象概念です。また、プロセスの実行状態も管理します。
　大半のプロセスはスレッドを1つしか持ちません。これをシングルスレッド（single-threaded）と呼びます。
複数のスレッドを持つプロセスはマルチスレッド（multithreaded）です。Unixの簡潔さの歴史に由来します
が、従来のUnixアプリケーションはシングルスレッドです。高速なプロセス作成や信頼性の高いIPCなど
の影響もあり、マルチスレッドが必要不可欠となる場面は多くありません。
　スレッドは専用のスタック（stack。ローカル変数の格納場所。スレッド非対応のシステムのプロセススタッ
クと同等）、プロセッサ状態、オブジェクトコードの現在位置（通常はプロセッサの命令ポインタ（instruction
pointer）が保持する）を持ちます。プロセスの他の部分のほとんどはすべてのスレッドで共有されます。
Linuxカーネル内部ではスレッドは独立したものとして実装されています。通常の単なるプロセスと同等
ですが、リソースの一部（もっとも重要なアドレス空間）を共有しています。ユーザ空間では、Linuxのスレッ
ド実装はPOSIX 1003.1c（pthreadと言います）に準拠しています。現在のLinuxのスレッド実装の名前は、
glibcの一部でもある、NPTL（Native POSIX Threading Library）です。
1.4.2.2　プロセスの階層
　各プロセスにはプロセスID（process ID、pid）という一意な正の整数が割り振られます。最初のプロセス
のpidは1で、以降のプロセスには連続した一意のpidが与えられます。
Linuxではプロセスは厳密な階層を構成します。これをプロセスツリー（process tree）と言います。プロセ
スツリーの最上位には最初のプロセスinitがあります。通常はinit（8）というコマンドです。新規にプロ
セスを作成するのはfork()システムコールです。fork()はコールした元のプロセスのコピーを作成します。
元のプロセスを親プロセス（parent）、新規に作成したプロセスを子プロセス（child）とそれぞれ呼びます。最
初のプロセスを除くすべてのプロセスには親プロセスが存在します。子プロセスよりも先に親プロセスが終
了した場合は、カーネルが子プロセスをinitプロセスへつなぎ直します（reparent）。
　プロセスは終了してもすぐにはシステムから削除されません。カーネルはプロセスの一部をメモリ内に残
しておき、親プロセスが子プロセスの終了状態を確認できるようにします。これをプロセスの終了待ち
（waiting on）と言います。親プロセスの子プロセス終了待ち合わせが完了すると、子プロセスは完全に破棄
されます。終了はしてもまだ終了待ち合わせが行われてないプロセスをゾンビプロセス（zombie）と呼びます。
initプロセスは定期的にすべての子プロセスの終了を待ち合わせます。つなぎ直されたプロセスが永久にゾ
ンビになってしまわないようにするためです。

1.4.3　ユーザとグループ
Linuxでの認証はユーザ（user）とグループ（group）という単位で管理されます。ユーザにはそれぞれユーザ
ID（user ID、uid）という一意な正の整数が割り振られます。プロセスにも、実行したユーザを識別できるよ
うに、このuidが対応付けられ、これをプロセスの実uid（real uid）と言います。Linuxカーネル内ではuidは
ユーザを表す概念に過ぎません。ユーザは自身や他のユーザを表すのにユーザ名（username）を使用します。
数字ではありません。ユーザ名や対応するuidは/etc/passwdに保存され、ライブラリがユーザ名とuidの
対応をマッピングします。
　ログイン処理ではユーザはユーザ名とパスワードをlogin（1）コマンドへ入力します。正当なユーザ名と正
しいパスワードが入力されると、login（1）コマンドは、/etc/passwdで指定されたユーザのログインシェル
（login shell）を起動し、シェルプロセスのuidをユーザのuidへ変更します。子プロセスは親プロセスから
uid を受け継ぎます。
uid 0 は root という特殊なユーザを表します。rootユーザは特権を持ち、システム上でほぼすべてのこ
とを行えます。例えばプロセスのuidを変更できるのはrootユーザだけです。このため、login（1）コマン
ドはrootユーザの権限で実行されます。
　プロセスは、実uid以外にも実効uid（effective uid）、saved uid、filesystem uid を持ちます。実 uid が常
にプロセスを起動したユーザを表すのに対し、実効uidは他のユーザ権限でプロセスを実行可能にするルー
ルの範囲内で、変化する場合があります。saved uidは元の実効uidを保存するもので、ユーザが実効uidを
変更する前のuidを必要とする際に使用します。filesystem uidは、通常は実効uidと同一ですが、ファイル
システムへアクセスする際の権限確認に使用されます。
　ユーザは1つまたは複数のグループに属します。/etc/passwdに記述したグループをプライマリグループ
またはログイングループ（primary or login group）と呼びます。その他にも補助的に複数のグループに参加可
能で、こちらは/etc/groupへ記述します。このためプロセスにも対応するグループID（group ID、gid）が存
在し、uid同様に実gid（real gid）、実効gid（effective gid）、saved gid、filesystem gidがあります。プロセ
スは通常ユーザのログイングループと関連付けられます。補助的に所属したグループではありません。
　プロセスが何らかの操作を行う際には、ある特定の条件に合致した場合にのみ、その操作を許可するセ
キュリティチェックが行われます。歴史的にUnixでは、単純な白か黒かでしか判断していませんでした。uid
が0のプロセスはアクセスが許可されるが、他のプロセスでは禁止するなどです。近年では、Linuxは従来
のセキュリティシステムをより汎化したケーパビリティ（capability）システムへ置き換えています。単純な2
値判断ではなく、ケーパビリティではより細かい単位で判断できます†。

1.4.5　シグナル
シグナル
（signal）とは非同期片方向の通信方法です。カーネルからプロセスへ送られる場合もありますし、
プロセスから他のプロセスへ、またプロセス自身へ送られる場合もあります。通常、シグナルは、アクセス
違反（segmentation fault）やユーザが割り込みキー（Ctrl-C）を入力したなど、何らかのイベントをプロセスへ
通知するために使用します。
Linuxカーネルでは約30種類（アーキテクチャにより異なります）のシグナルを実装しています。シグナル
は数値または名前を用いて表します。例えば、端末のハングアップを意味するシグナルSIGHUPの値は、i386
アーキテクチャでは、1です。
† 訳者注：書き込み権限があれば、新たなファイル（リンク）作成以外にも、もちろんファイル削除も可能となりま
す。よく誤解されるのですが、ファイルを削除できるか否かを決定するのは、そのファイルのパーミションでは
なく、親ディレクトリのパーミションです。読み取り専用ファイルでも、親ディレクトリに対する書き込み権限
を持っていれば、削除可能です。ファイルシステムによっては独自の属性を追加しており、変更不可、追加書き
不可、ダンプ対象外などの属性を与えられます。
1.4　Linuxプログラミングの概念
　プロセスはシグナルを受け取った際の動作をカスタマイズできます。しかし例外があります。SIGKILLは
常にプロセスを終了させ、またSIGSTOPは常にプロセスを停止（実行の中断）させます。この2つのシグナル
の動作は変更できません。シグナルを受け取った際のデフォルトの動作は、シグナルの種類により異なりま
す。単にプロセスを終了するものもあれば、コアダンプし終了する、実行を中断する、または何もしないも
のがあります。プロセスはデフォルトの動作をそのまま使用することも、独自のシグナル処理を明示的に追
加したり、または無視することも可能です。無視されたシグナルは何も処理されず破棄されます。独自のシ
グナル処理を加えた場合は、ユーザ定義のシグナルハンドラ（signal handler）関数が実行されます。プロセス
はシグナルを受け取ると、即座にシグナルハンドラ関数へ制御を渡し、シグナルハンドラ関数が処理を終え
ると、割り込まれた元の位置へ制御を戻します。
1.4.6　プロセス間通信
　プロセスが互いに情報をやり取りし、イベントを通知できるようにする仕組みもオペレーティングシステ
ムの重要な仕事の1つです。Linuxカーネルでは、System VとPOSIXの両方で定義/標準化された、従来
からあるUnixのIPC（プロセス間通信、interprocess communication）だけではなく、独自の仕組みも追加し
ています。
LinuxのIPCには、パイプ（pipe）、名前付きパイプ（named pipe）、セマフォ（semaphore）、メッセージキュー
（message queue）、共有メモリ（shared memory）、futex（Fast Userspace muTex）があります。
1.4.7　ヘッダファイル
Linuxのシステムプログラミングではヘッダファイルの利用は欠かせません。システムプログラミングで
使用するヘッダファイルはカーネル、またはglibcに含まれるもので、C言語の標準機能である<string.h>
や、Unixが通常備えている<unistd.h>などがあります。
1.4.8　エラー処理
　言うまでもないことですが、エラーチェック、エラー処理は決して欠かせない重要なものです。システム
プログラミングでは、関数の戻り値または専用のグローバル変数errnoがエラーを表します。glibcのerrno
はライブラリ関数、システムコールの両方に対応しており、特に意識せずに使用できます。本書で解説する
インタフェースのほとんどが、上記の仕組みに基づきエラーを処理します。
　関数はコール元に対し、戻り値を用いてエラーを通知します。-1が一般的に使用されますが、関数により
値は異なります。戻り値は何らかのエラーが発生したことを示すだけで、その原因についての情報は持ちま
せん。エラーの原因はグローバル変数errnoが表します。
errno は、<errno.h> で次のように定義されています。
extern int errno;
errnoの値を使用できるのは、関数がエラーを返した直後だけです。関数はerrnoを設定し（通常は）-1を
返します。エラーが発生しない場合でも、関数はerrnoを変更する場合があります。この変更は標準に違反
しているわけではありません。

　まずperror()というライブラリ関数があります。
#include <stdio.h>
void perror (const char *str);
perror()は、errno の現在の値に対応したエラーメッセージを標準エラー出力（standard error、stderr）

if (close (fd) == -1)

strerror()およびstrerror_r()というC ライブラリ関数もあります。
#include <string.h>
char * strerror (int errnum);
int strerror_r (int errnum, char *buf, size_t len);
strerror()はerrnumに与えられたエラーに対応するエラーメッセージ（文字列）へのポインタを返します。
アプリケーションからは文字列を変更することはできません。また再度perror()やstrerror()をコール

発生時には-1を、それぞれ返します。面白いことにエラー発生時にはerrnoも設定します。
　少数ですが、戻り値がどんな値にもなりうる関数もあります。この場合には、コール前にerrnoへ0を代
入しておき、コール後に0か否かを確認する必要があります。この種の関数は、エラー発生時にerrnoへ設
定する値が0以外であることが保証されています。サンプルコードを挙げます。
errno = 0;
arg = strtoul (buf, NULL, 0);
if (errno)
        perror ("strtoul");
errnoの確認処理でよくある誤りは、どんなライブラリ関数、システムコールでもerrnoを上書きし得る
という点を忘れてしまうことです。例えば、次のサンプルコードにはバグがあります。
if (fsync (fd) == -1) {
        fprintf (stderr, "fsync failed!\n");
        if (errno == EIO)
                fprintf (stderr, "I/O error on %d!\n", fd);
}

　関数コールに跨りerrnoを使用する場合は、一度退避する必要があります†。
if (fsync (fd) == -1) {
        int err = errno;
        fprintf (stderr, "fsync failed: %s\n", strerror (errno));
        if (err == EIO) {
                /* if the error is I/O-related, jump ship */   I/O関連のエラーの場合は処理中止
                fprintf (stderr, "I/O error on %d!\n", fd);
                exit (EXIT_FAILURE);

}

マルチスレッドの場合はerrnoはスレッドごとに用意されており、スレッドセーフになっています。
